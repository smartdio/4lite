# 从记忆到校园：《记忆中的学校》开发纪实

记录日期：2026年8月22日
记录范围：从项目最初构想到当前版本
项目形态：基于 Three.js 的浏览器三维校园体验

## 前言

这个项目的起点，不是一套完整的建筑图纸，也不是一份已经写好的游戏策划案，而是一段关于旧校园的个人记忆。

记忆里有一座校门，有前院、教学楼、操场、旧教室、厕所、教师宿舍，也有一棵很大的榕树。人还记得教学楼是什么颜色，门窗大致怎样排列，厕所入口怎样转弯，宿舍旁边的高台和树根怎样连接，教室里有哪些课桌、黑板、粉笔和旧课本。但这些内容并不是一次性、完整地出现的。它们散落在一张记忆性插画、陆续画出的草图、少量历史照片、一些尺寸估算，以及开发过程中不断被唤起的口述细节里。

因此，这个项目从一开始就不是普通的“照图建模”。它更像一次由人和 Agent 共同完成的空间考证：人负责提供记忆、判断和感受，Agent 负责把零散材料整理成可以讨论的资料，把模糊关系转换成图纸和参数，把确认后的内容实现成三维场景，再把浏览器中的结果交还给人重新观看和校正。

整个校园就是在这种往返中逐渐形成的。

## 一、最开始的构想

最初的目标，是在浏览器中还原一座20世纪80年代初的广东小学校园。它不是只能从远处观看的建筑模型，而是一个可以真正走进去的地方：玩家从校门进入，穿过一号教学楼中央的门洞，到达后方操场；可以沿走廊行走，进入教室，上下楼梯，观察门窗、课桌、黑板和墙上的宣传画。

项目想保留的也不只是建筑外形，而是一种很具体的记忆气氛：盛夏接近正午，校园明亮、安静而空旷；墙面已经褪色，旧瓦、木门和水泥地带着年代感；阳光很强，但阴影仍然通透；树叶和树影缓慢变化，时间仿佛停留在童年。

这意味着项目同时存在两个目标。

第一个目标是“还原”：建筑之间的关系、门窗数量、走廊方向、楼梯位置、地面高差和树木位置要尽量符合亲历者记忆。

第二个目标是“表达”：画面不能像冷冰冰的建筑测绘，也不能成为阴森破败的废墟。它应该是温暖的、手绘的、有一点褪色，却仍然明亮而有生命力。

这两个目标后来一直贯穿整个开发过程。空间必须有依据，美术必须有情绪；情绪不能掩盖空间错误，准确也不能让场景失去记忆感。

## 二、为什么没有直接把插画变成三维场景

最早的一张校园图是一幅记忆性鸟瞰插画。它很好地表现了校园中有哪些建筑、树木和场地，也传达了整体气氛。但它并不是测绘图。

图里的透视会弯曲，一些重要物体被有意放大，建筑的可见立面可能为了叙事被翻转，树冠遮住了后面的空间，没有画出的地方也不等于现实中不存在。单凭这张图，无法可靠判断建筑进深、每层房间数、楼梯转向、背立面开口或校园真实尺寸。

早期曾出现过根据插画快速生成 Three.js 空间的尝试，但这个结果很快被放弃。原因并不是它不能产生一幅“像校园”的画面，而是它把大量没有依据的猜测同时固化了。画面越完整，反而越容易让人误以为那些尺寸和关系已经被确认。

项目由此确定了一条重要原则：不使用单张图片直接生成整个校园，不从艺术化插画反推准确三维尺寸，也不把未经确认的早期原型当作后续依据。

插画继续被保留，但它的职责发生了变化。它用于说明情绪、建筑特征和相邻关系，而不是替代平面图、尺寸表和亲历者确认。

## 三、先整理记忆，再开始建模

正式开发的第一步不是写 Three.js，而是建立资料体系。

Agent 把用户提供的校园总图、教学楼草图、厕所草图、教师宿舍草图、旧教室草图、门窗草图、栏杆草图和历史照片分别归档。每一份重要资料都配有文字说明，记录四类内容：

- 用户明确说了什么；
- 图中能够直接看出什么；
- Agent 根据资料推测了什么；
- 还有什么无法确定。

为了避免推测被误写成事实，项目建立了 A、B、C、D 四级可信度。

- A 级表示亲历者明确确认、具有清晰尺寸，或者多份资料能够互相印证；
- B 级表示有较强依据，但仍缺少尺寸或另一角度；
- C 级表示为了推进第一版而采用的工作候选；
- D 级表示资料不足，暂时保持未知。

这个制度后来非常有用。三维场景不能没有尺寸，因此有些地方必须先填入工作值；但只要它仍被标记为 C 级，用户后来想起新信息时，Agent 就可以定点修改，而不需要推翻全部结构。

资料整理也改变了人和 Agent 的沟通方式。Agent 不再只回答“我看懂了”，而是把理解写成可以检查的句子。例如：厕所没有窗，正面中部先进入共用入口，再沿屏风墙内侧分别向左右走，最后转入男女两端门洞。用户如果发现其中某一处不对，可以直接纠正具体关系。

只有当文字关系大致正确之后，Agent 才把它画成干净的 SVG 平面图或立面图。

## 四、从校园关系图到米制平面

项目没有立刻追求每栋楼的精确长度，而是先确认校园的拓扑关系，也就是“谁在谁的旁边，哪里能够通过”。

最先稳定下来的是一条主要空间轴线：从南侧校门进入前院，面对两层 U 形的一号教学楼；穿过楼体中央门洞，进入后方主操场；主操场另一端是一栋三层的二号教学楼，东侧还有厕所、沙池、旧教室、活动场、教师宿舍和大榕树所在的高地。

随后逐步确认了几项对全局影响很大的关系：

- 一号教学楼是两层 U 形建筑，中央门洞贯通前后院；
- 二号教学楼为三层，中央设置楼梯，教室沿连续外廊排列；
- 厕所和沙池位于较低地面；
- 旧教室、旧教室前活动场和教师宿舍位于同一块连续高台；
- 教师宿舍前方的高台局部形成土墩，大榕树生长在这里；
- 高台边缘是自然土坡，不是若干互不相连的水泥基座。

这些关系一旦确认，校园才真正从一幅插画变成一张可以行走的平面。

尺寸标定则从人比较容易记住的对象开始。标准教室约为9×7米，走廊约1.5至2米宽，教学楼层高约3.1米，再配合门、窗、楼梯踏步、乒乓球台和运动场等常见尺度，逐步反推建筑和场地比例。

项目统一规定一个 Three.js 世界单位等于一米。所有重要尺寸、坐标、地形轮廓和资产地址被集中写入 `src/campus-config.js`。这样，当用户说“这棵树太高”“高台应该更靠东”“这条走廊太宽”时，Agent 修改的是一套统一参数，而不是在不同模型里分别猜测。

## 五、灰盒：让人真正走进记忆里检查

二维关系确定后，项目进入灰盒阶段。

灰盒不是最终美术模型。它只用简单色块和基础几何建立墙、楼板、屋顶、门窗洞、走廊、楼梯、平台、围墙和地面。这个阶段的目的，是在复杂材质和漂亮树木加入之前，验证空间本身是否成立。

Agent 直接在最终使用的 Three.js 场景中搭建灰盒，而不是先在 Blender 里做一个封闭的完整校园。这样做的好处是，建筑尺寸、玩家碰撞、第一人称视线和最终运行环境从一开始就在同一套坐标里。

一号教学楼和二号教学楼的大部分规则结构由代码生成。墙体、楼板、柱梁、教室开口和栏杆都由集中参数驱动。不同楼层的完成面、楼板厚度、门窗标高和楼梯踏步都可以统一调整。

灰盒验证有两种主要视角。

一种是鸟瞰，用来检查校园整体布局、建筑距离、地形边界和树木位置。

另一种是第一人称，用来检查更难从图纸发现的问题：从校门看进去时楼体是否太压迫，中央门洞是否够宽，走廊是否自然，台阶能否跨越，楼梯是否会卡住，站在教室里看到的窗台和黑板高度是否合理。

很多真正影响体验的问题，都是在行走中才暴露出来的。

例如，一号楼曾出现门窗像嵌进楼板的问题。原因不是门窗模型本身，而是楼板厚度从“完成面”向上生长，占用了室内空间。后来楼板被改为从完成面向下生成，门底、窗台和层高才重新对齐。

楼梯和栏杆也是一样。画面上看似正确的栏杆，如果没有带高度范围的碰撞，玩家仍然可以从中穿过；只按单层地面计算高度，玩家也无法顺利上到二层。Agent 最终为台阶、梯段、平台和多层楼板建立统一地面采样，并为栏杆、楼梯半墙和临空边缘增加碰撞。

灰盒阶段让项目第一次具备了一个重要能力：用户不再只是“看图回忆”，而是可以通过虚拟行走判断这个空间像不像记忆中的校园。

## 六、人与 Agent 怎样通过草图合作

手绘草图是本项目最重要的沟通媒介之一。

用户不需要把草图画成专业建筑图。很多图只是快速画出门窗顺序、楼梯方向、厕所入口转折、高台边缘或树的位置。Agent 的任务不是把草图当成绝对精确的线稿照抄，而是从中提取结构关系，并明确哪些内容仍然不能确定。

一张草图通常会经历以下过程：

1. 原图被保存并编号；
2. Agent 把用户的口述和图中信息写成说明；
3. 明确哪些是已确认事实，哪些只是从线条推读；
4. 列出缺失的尺寸、背面或构造问题；
5. 绘制一版干净的平面图、立面图或结构示意；
6. 用户确认或纠正；
7. Agent 将结果转成 Three.js 参数或 Blender 建模约束；
8. 浏览器中出现第一版后，用户再次根据实际画面判断。

旧教室是这个过程的典型例子。

早期草图中的简略线条一度被理解为每间教室“门—窗—门”。后来用户明确记起，每间其实是两侧各一扇门，中间连续三扇窗，也就是“门—窗—窗—窗—门”。Agent 随即废止旧结论，更新参考说明、平立面约束、概念图和正式 GLB。最终整栋两间教室的正面形成四门六窗。

这个修改看起来只是多了几扇窗，实际上说明了项目中一个重要原则：草图不是一次性冻结的施工图，记忆也会在看到模型之后继续恢复。只要用户给出新的明确判断，整个资料链就应该同步更新，不能只在模型上临时补一块。

厕所草图提供了另一种信息。用户记得的重点不是瓦片数量或精确屋脊角度，而是使用者如何进入：先从正面共用入口进入，两侧有平行屏风墙，向左或向右走到尽端后再转入门洞，而且建筑没有窗，墙顶与屋顶之间有连续通风带。Agent 因此把主要精力放在入口拓扑、无窗立面和通风结构上，没有为不可进入的厕所虚构完整室内。

教师宿舍草图则帮助确认了建筑与地形的关系。它不仅说明宿舍是两层、门窗朝西、南侧有露天楼梯，也说明宿舍、旧教室和活动场共同位于连续高台上。这个信息最终改变的不只是一个建筑，而是整个校园东侧地形的生成方式。

## 七、从参考图到概念图，再到 GLB

当空间关系和尺寸已经确认，项目才开始制作具有独特轮廓的正式资产。

这里同样没有采用“图片直接变成完整校园”的方式，但会在明确的结构约束下，用概念图帮助确定单个建筑或物件的美术方向。厕所、教师宿舍和旧教室都经历了这样的过程：先根据草图与场景截图形成概念图，用户选择或修改，再制作 Blender 源模型和游戏版 GLB。

概念图解决的是“它应该长什么样”，结构文档解决的是“它必须满足什么关系”，Blender 则负责把两者变成具有正确米制比例、法线、UV、原点和层级的三维资产。

正式 GLB 接入前，Agent 会检查：

- 模型单位是否为米；
- 朝向是否与校园坐标一致；
- 原点是否方便落位；
- 门、窗或其他可动物体的 Pivot 是否在正确转轴；
- 法线和透明材质是否正常；
- 近景轮廓是否符合用户确认的概念图；
- 模型是否需要降面或缩小贴图；
- 视觉模型是否应该和简化碰撞体分离。

木门的铰链问题体现了这种检查的重要性。早期门扇虽然能够旋转，但 Pivot 不在铰链中心，开门时门板会产生不自然的位移。后来 Agent 在 Blender 中把根节点转轴移动到铰链中心，再对门板子节点做反向补偿，使门在关闭时位置不变，打开时又能绕正确轴线旋转。

水泥滑梯则体现了“源资产”和“游戏资产”的区别。原始模型约85 MB、150万三角面并使用多张4096像素 PNG，直接放入浏览器会带来不必要的下载和渲染负担。它后来被整理为约3万三角面、1024像素 WebP贴图和量化后的游戏版，再进一步做保守的 Meshopt 压缩。最终浏览器中的滑梯仍保留用户认可的轮廓和约2米真实高度，但运行成本大幅下降。

## 八、大榕树为什么做了那么多版本

大榕树是整个项目中最复杂、修改次数最多的独立资产之一。

它不仅是一棵树，也是校园东侧空间的重要记忆锚点。树干、主枝方向、板根、气根、树冠高度、叶簇疏密、土墩和石质底座都会影响用户对场景的判断。

制作并不是一次完成的。Agent 先根据参考图和口述建立树的总体设定，再在 Blender 中不断调整主干骨架、一级到三级分枝、树冠分层、叶片卡片、板根、气根和底座。过程文件保留了大量版本，每个版本都针对一个明确问题，例如树冠太像均匀扇形、上部树干太空、叶簇没有落在枝梢、底座石块像一整圈规则模型等。

用户会同时查看 Blender 预览和校园中的实际效果。因为一棵树在单独预览中看起来合理，放入校园后仍可能太高、太重、遮住建筑，或者让操场尺度显得错误。

树叶材质也带来过问题。透明叶片在压缩、缩放或 Alpha 裁切不当时会出现白边。解决方法不是简单把透明阈值调高，而是一起处理叶片图集透明边缘的颜色、Alpha Test、贴图压缩和逆光表现，并在近景与远景同时检查。

项目还为榕树评估过运行时 LOD，希望按距离加载不同精度模型。技术上曾完成三档模型、渐进加载、失败回退和测试，但用户最终决定保留单一完整模型。Agent 随后完整移除了运行时 LOD，而不是让废弃逻辑继续潜伏在代码中。

后来，榕树与一棵较高的操场树又根据实际场景感受统一缩至约8米。这个决定说明，模型制作得越精细，越不能脱离校园整体尺度来判断。

## 九、艺术方向是怎样确定的

项目最初只有“怀旧”“手绘动画感”“像童年记忆”这样的感受描述。Agent 需要把这些词转换成可以执行和检查的视觉规则。

最终确定的方向是：原创的赛璐璐色块配柔和水彩过渡，盛夏接近正午，阳光明亮，阴影偏蓝绿但保持通透，建筑和植物有清楚轮廓，整体温暖却不过度橙黄。

项目明确避开几种方向：

- 不做照片级写实；
- 不做阴森、废墟或恐怖校园；
- 不使用过重的复古黄滤镜；
- 不用高饱和塑料卡通色；
- 不直接复制某一部现有动画的具体镜头、人物或专有设计；
- 不用全屏纸纹和噪点假装“水彩”。

用户提到的动画式怀旧感，最终被转译为这个项目自己的语言：大色块清楚，水彩变化低频，墙面褪色但不污黑，阳光温暖，阴影有空气感，旧设施仍然可亲而不是可怕。

这套方向被写入艺术规范和材质规范，成为后续所有墙体、木门、铁窗、瓦顶、树木和校园文化图像的共同依据。

## 十、墙面和地面材质是怎样制作的

校园主体的大部分墙体由 Three.js 程序化生成，不能像普通单体模型那样依赖手工展开的完整 UV。因此墙面材质采用了适合参数化建筑的制作方式。

首先根据建筑类型确定基准色。一号楼外墙为米白，结构构件偏黄色；二号楼外墙为赭黄；两栋楼室内墙和天花为白色偏暖。然后为每一类墙面制作四张水彩变体。

这些贴图并不追求照片污渍。它们主要包含低频的色差、褪色、水痕和少量旧化。米白墙使用暖麦黄和浅褐米色变化，赭黄墙使用茶褐和黄褐变化，室内白墙还加入极少的淡蓝灰空气色。黑灰污迹被严格限制，因为它会让校园从温暖的旧建筑变成阴森废墟。

在 Three.js 中，墙面使用世界坐标连续投射。横向纹理尺度按现实米数控制，图案可以镜像重复；竖向每经过一层3.1米重新对齐。每一段墙根据稳定的名称散列选择四个变体之一，因此相邻区域不会全部复制同一块斑驳，页面刷新后也不会随机跳变。

第一轮墙面旧化曾经偏重，尤其是赭黄墙看起来太脏。最后的解决方式不是增加曝光或把灯光调白，而是直接回到贴图，把墙面分别向各自基准色回混。这样既保留了水彩变化，也重新恢复了整洁、温暖的记忆感。

围墙和校门柱采用另一种图集方法。围墙有 A、B 两幅完整墙面，运行时合并成 WebP 图集，沿长墙连续投射并交替镜像。校门柱则使用包含四个柱面的青灰石材图集，使四个方向的纹理不完全相同，底部潮痕也能落在合理位置。

地面和高台材质经历了类似反复。大面积不规则地面如果直接拉伸一张贴图，会产生明显变形；如果只增加许多裂缝贴片，又容易显得像随意贴上去的装饰。最终做法是先划分水泥、泥地、沙地和高台区域，控制世界尺度与投射方向，再少量加入手绘裂缝、色差和接触阴影。

## 十一、独立模型的材质怎样制作

厕所、宿舍、旧教室、沙池、滑梯、门窗和树木等独立 GLB，使用 Blender UV 和材质图集。

制作顺序通常是：先确认比例和轮廓，再展开 UV，随后制作基础色、粗糙度、法线或透明叶片图集。项目的主要美术信息放在基础色里，法线和高光只用于帮助体积，不追求强烈的写实 PBR 效果。

不同类型贴图采用不同压缩策略。普通颜色图可以使用高质量有损 WebP；法线、金属度和粗糙度等数据图不能接受颜色偏差，因此只使用无损 WebP。树叶带有透明边缘，压缩时还要额外检查 Alpha 质量。

所有候选都要回到浏览器中检查。Blender 中的材质预览不能代替真实场景，因为最终还有 Three.js 灯光、阴影、色彩空间、雾化、视距和周围建筑反光的影响。

## 十二、课本、作业本和宣传画怎样进入校园

当建筑和大环境稳定后，项目开始加入真正属于学校日常生活的东西：走廊宣传画、校规、奖状、黑板报、教室标语、旧课本、作业本、粉笔盒和粉笔。

这部分图像分成两类。

第一类是原创的年代化图像，例如校园劳动、学习纪律、文明礼貌等宣传画。参考图只用于理解1980年代初的配色、印刷和构图习惯，人物、动作和整体画面重新创作，不复制参考图的面孔、文字、水印或完整构图。

第二类是历史封面复原，例如旧语文、数学和历史课本。这类任务不能随意重画。Agent 使用受约束的精确图像编辑，把斜放、低清或带背景的封面恢复成正面图，尽量保持人物、姿势、物件、标题、册次、出版社文字和原有留白。只移除桌面、相邻书本、透视和投影，对缺边部分做最小延续。

所有图像都保留不同层级的文件：生成或修复过程图、高清母版和运行时 WebP。Python 与 ImageMagick 脚本负责统一裁切、缩放和导出，避免手工处理几十张图时出现尺寸和质量不一致。

运行时没有在每张课桌上都复制大量高清书本，而是选择少量代表性位置稀疏放置。这样既能让教室有生活痕迹，又能控制纹理和绘制成本。

## 十三、从“能看”到“能玩”

项目的前半段主要解决空间和视觉，后半段开始增加第一人称体验和互动。

完整场景最终默认从校门进入。开场镜头从校园东南侧空中缓慢飘落，速度逐渐减慢，然后过渡到校门前的第一人称。桌面端由进入按钮的同一次用户手势请求 Pointer Lock，减少进入后还要再次点击的割裂感。

第一人称移动并不只是增加 WASD。Agent 还需要处理地面采样、楼梯、台阶、楼板、门洞、栏杆和室内家具碰撞。为了让玩家能够穿过老教室中较窄的通道，同时又不穿墙，玩家碰撞半径最终调整为0.20米。

交互规则逐步统一为：玩家与物体距离不超过2.5米，射线没有被墙体或其他实体遮挡，才能触发。门窗、课桌、黑板、粉笔和粉笔盒都遵循同一距离逻辑。

移动端则不能照搬桌面端。早期审计发现，手机虽然可以拖动视角，却没有办法移动，因为场景仍然只读取键盘。后来加入左侧虚拟摇杆、右侧拖动观察、触摸安全区和横竖屏布局。

触摸交互最初直接从手指位置发射射线，但这会和拖动观察冲突。最终改为轻触后使用屏幕中心准星执行通用交互。这样无论点击门、课桌还是粉笔，手机端都遵循同一套空间瞄准方式。

## 十四、黑板与粉笔：一个小交互怎样逐步变完整

黑板绘画最初只是“让玩家在黑板上画线”的想法，真正实现时却涉及视角、坐标、存储、触摸和状态管理。

玩家接近教学黑板并从正面进入绘画模式后，鼠标或触摸输入会被映射到黑板自身的二维坐标。绘画内容被绘制到纹理画布上，再更新到三维黑板表面。用户可以绘画、擦除和清空，22块教学黑板分别保存自己的内容。

为了让内容刷新页面后仍然存在，项目建立了统一的浏览器本地用户数据层。它带有版本和命名空间，不让黑板功能直接散乱地读写 localStorage，也为未来保存其他个人状态留下统一入口。

粉笔交互则进一步发展成一个小型状态系统。玩家可以从讲台拾取粉笔，按住后蓄力，再将粉笔抛出。粉笔会与教室地面、墙壁和家具发生简化物理碰撞，落地后还能再次拾取。

过程中出现过一个明显问题：拾取粉笔后，手中已经有一支粉笔，但讲台上的静态实例仍然可见。原因是静态展示物、手持物和物理对象各自维护状态，没有统一所有权。后来拾取时会彻底移除对应的讲台实例，每间教室维护六支粉笔活动池；玩家离开教室时重置，点击粉笔盒则可以把全部粉笔一键收回。

这个交互最终形成了“静态摆放—手持—飞行—碰撞—落地—再次拾取—归位”的完整闭环。

## 十五、性能问题是怎样发现的

场景越来越完整后，性能问题不再能靠主观感觉判断。项目开始建立可重复测量的基线。

Vite 负责开发与构建，Playwright 在 Chrome 中运行固定测试。自动化记录构建体积、运行资产数量、入口 JavaScript、draw calls、三角面、纹理数量、估算显存、场景就绪时间和帧耗时 P95。六个固定截图视角覆盖全校鸟瞰、校门、一号楼院内、主操场、旧教室活动场和宿舍／滑梯区域。

第一轮完整场景审计发现，真正的弱网瓶颈不是 GLB 解析，而是资源传输。18个主要 GLB 中，内嵌图片占总体积约八成。在本地，场景不到一秒就能准备好；但模拟20 Mbps带宽和100毫秒延迟时，完整加载需要约17秒。

这项测量改变了优化顺序。Agent 没有先大规模破坏模型轮廓来降面，而是优先处理占比最大的内嵌 PNG：颜色图转为高质量 WebP，法线和数据图转为无损 WebP，共享水泥纹理提前调度。之后才对适合的建筑和滑梯使用保守 Meshopt。

这也是整个项目反复坚持的做法：先找出瓶颈，再决定工具。文件大不一定是几何问题，帧率低也不一定要牺牲画质。

## 十六、哪些优化尝试最后没有采用

项目中有几次技术上可行、最终却没有成为正式方案的尝试。

### 榕树 LOD

项目曾为大榕树制作三档精度和渐进加载，甚至测试了高精度加载失败时继续显示低精度模型的回退。但用户更希望所有时候都看到完整树形，最终决定全项目不使用运行时 LOD。Agent 随后撤销相关运行逻辑，保留报告作为历史记录。

### KTX2 压缩纹理

共享水泥纹理曾被制作成 KTX2 候选。UASTC 版本在 GPU 显存和体积方面表现很好，但只为一张纹理引入 KTX2Loader、Basis JavaScript 和 WASM，会增加多个基础设施请求；ETC1S 版本还在近景产生明显黑边。最终 KTX2 保持为试验开关，没有成为默认运行方案。

### 单请求核心资产包

项目也尝试过把多个核心资产打成单一请求，希望减少弱网下的请求开销。实测后，用户认为这种方式增加耦合，收益不足以改变现有架构，于是正式运行恢复为独立 GLB 加共享 WebP。

这些实验没有被视为失败后删除。候选、测试数据、撤销原因和恢复方式都保存在报告与归档中。这样后续开发者不会在不了解前因的情况下重复同一轮尝试。

## 十七、加载界面为什么必须等到最后一刻

在移动端和弱网优化过程中，曾讨论过是否应该先让用户进入一个不完整的校园，再在后台逐步补全模型。

用户当时明确选择：基础校园必须完整预载，加载框只有在必需模型、纹理、材质、碰撞和首次 GPU 帧全部准备好之后才能关闭。这个决定针对的是“不能让尚未准备好的校园提前露出来”，而不是禁止后续在资源已经载入之后，根据玩家所在位置管理哪些室内细节参与渲染。后来采用的教室级 LOD 仍然保留完整预载和完整近景模型，只改变运行时可见集合。

实现时还发现，仅等待业务代码中的 Promise 不够。Three.js 的 GLB 内嵌图片可能仍在解码和上传，数字已经显示加载完成，画面却还没有真正稳定。Agent 因此加入物理资源完成屏障，并把首次 GPU 帧也纳入放行条件。

这个修正区分了三个过去容易混在一起的概念：文件下载完成、资源解析完成，以及玩家可以安全进入。项目最终选择以第三个状态作为入口标准。背景音乐后来被明确排除在这道屏障之外：音乐可以稍后准备，但其余画面资源仍然一起出现，避免视觉上零散拼装。

## 十八、测试、归档与回退

随着项目复杂度增加，每次修改都可能影响远处另一块区域。改一种共享墙面材质，可能同时改变两栋楼；调整玩家碰撞，可能让楼梯更顺，却让门洞失效；压缩树叶贴图，可能让远景更快，却在近景出现白边。

为此，项目建立了多层验证：

- 每次生产构建检查文件体积和数量预算；
- 浏览器记录绘制调用、三角面、纹理和帧耗时；
- Playwright 对六个固定视角做截图回归，最大像素差容限为0.8%；
- 自动测试覆盖碰撞、门窗、触摸、加载、黑板和粉笔；
- 真实浏览器近景继续由人检查色彩、透明边缘、材质接缝和操作手感；
- 高风险修改先输出到 `artifacts/`，通过后才替换正式资产；
- 替换前的运行资产保存到 `archive/phase-*`，报告记录参数、哈希、体积和恢复方法。

项目中的 `handoff.md` 也承担了特殊作用。它不是这篇叙事文章，而是一份持续增长的工程交接账本。每次用户确认的重要尺度、材质、交互和性能决定都会写进去，并标记哪些结果不得回退。这样即使开发跨越多个对话，新的 Agent 仍然能够知道当前有效基线，而不会误把历史方案当成新任务。

## 十九、这次人机协作是怎样运转的

回看整个过程，人和 Agent 并不是传统意义上的“甲方与执行者”。两者更像拥有不同能力的共同创作者。

人掌握 Agent 无法自行获得的东西：亲历记忆、空间直觉、对“像不像”的判断、对某棵树或某个门洞的情感权重。一个模型尺寸可能符合常见建筑规范，但亲历者站在校门前觉得“太高了”，这个判断仍然重要，因为项目还原的是这所具体学校，而不是一所统计意义上的平均学校。

Agent 则负责把这些感受转成可操作的中间层：证据说明、未知项、SVG图纸、米制参数、Blender资产、贴图、代码、碰撞、测试和恢复路径。Agent 也负责在用户没有给出完整技术表达时提出一种可验证解释，而不是要求用户先学会三维建模术语。

双方最常见的对话循环是：

1. 人提供一张草图、一张参考图、一段记忆，或指出画面中的不对；
2. Agent 复述理解，标出确定与不确定内容；
3. Agent 制作最小可判断版本；
4. 人根据图纸、截图或第一人称体验确认与纠正；
5. Agent 修改资料、参数、模型和测试；
6. 结果被确认后归档，成为下一轮的基线。

这种循环比一次性长需求更适合记忆还原。很多细节只有在人看到第一版后才会被重新唤起。如果 Agent 把第一版当成终稿，项目会充满未经察觉的猜测；如果人必须一开始就把所有细节讲全，项目又根本无法启动。

双方真正共享的不是一份完美需求，而是一套允许逐步逼近的工作方法。

## 二十、项目过程中形成的经验

### 1. 先让理解可检查

面对草图和口述，最重要的不是尽快生成模型，而是先把 Agent 的理解写出来。只要理解可以被检查，错误就能在成本最低的时候被纠正。

### 2. 不确定并不等于不能开发

可以使用候选尺寸，但必须标明它是候选。好的系统不是假装没有未知，而是让未知保持可替换。

### 3. 先做小样，再批量展开

一段墙、一扇门、一棵树、一张宣传画先确认风格，远比一次制作几十个资产更安全。小样的意义是让抽象审美变成具体选择。

### 4. 最终媒介才是最终判断场所

建筑不能只看图纸，树不能只看 Blender，材质不能只看贴图。所有内容都必须回到真实浏览器，在正确光照、视距、相邻物体和第一人称尺度中判断。

### 5. 感受性反馈也能转换成工程参数

“太脏”可以变成降低旧化对比并向基准色回混；“太高”可以变成8米尺度；“太窄”可以变成0.20米玩家半径；“点不到”可以变成2.5米统一交互距离。Agent 的重要职责，就是完成这种翻译。

### 6. 修改要贯穿整条资料链

旧教室多三扇窗，不只是改 GLB。参考说明、平立面规则、概念图、碰撞、场景截图和测试都应该同步更新。否则旧错误会在下一轮重新回来。

### 7. 优化不是数字竞赛

文件更小、请求更少、三角面更低都不是单独成立的目标。只有在用户确认的视觉、空间和交互不被破坏时，优化才有意义。

### 8. 被否决的实验也应留下记录

LOD、KTX2 和单包方案虽然没有成为正式版本，却提供了明确结论。保存这些结论，可以避免未来再次付出同样成本。

### 9. 交接文档是长期共同记忆

跨越多个对话的项目，需要一个比聊天上下文更稳定的地方保存已经确认的事实、历史方案、失败原因和恢复路径。这个项目能持续推进，很大程度上依赖这种外部化的共同记忆。

## 二十一、篮球怎样从场景摆设变成自由互动

校园日常物件逐渐丰富之后，项目开始加入更完整的运动体验。第一项是篮球。

篮球最初只是三只摆在升旗台附近的静态资产。为了制作它们，Agent 没有直接采用下载模型中附带的成品 GLB，而是检查源文件、清除无关物体、重新绑定材质，并把球体规范为约24厘米的真实直径。球的颜色也经过专门设定：褪色的暖橙棕，没有现代品牌标志，有适度磨损，但仍然像一只可以继续使用的旧篮球。

真正进入互动阶段后，用户又纠正了篮球架的位置。它不在东侧高台，也不在最初设想的升旗台旁，而是在天梯南侧的主水泥地，靠近从东往西数的第二棵马尾松，篮圈朝南。这个调整再次说明，运动设施不能只按空地随意摆放；它与某棵树、某段水泥地之间的关系，本身就是记忆的一部分。

正式玩法没有把篮球变成一个独立关卡。三只球仍然留在校园里，玩家靠近后可以拿起、蓄力投掷，也可以直接推动或踢动。球使用固定时间步长进行局部物理计算，会与地面、篮板、分段篮圈和篮球架主要结构碰撞，并根据水泥、泥地等表面产生不同弹跳与滚动。合法进球必须先经过篮圈上方，再向下穿过篮圈平面，避免球从下方穿入也被误判得分。

动态阴影带来了一个很有代表性的问题。校园的太阳阴影在完整加载后会被冻结，以节省持续渲染成本；如果篮球继续写入这张阴影图，球离开原位后，地面会留下三个不会移动的“幽灵影子”。Agent 最后没有重新开启全场实时阴影，而是为每只篮球制作解析式投影椭圆，根据太阳方向、球的高度和实际地面高度实时改变位置、大小与深浅。它既让玩家能够判断落点，也避免整座校园为三个小球重复刷新阴影。

篮球还加入了拿球、出手、落地、篮板、篮圈和进球音效。它最终形成了一个与校园行走自然连接的自由互动：没有必须完成的任务，也不保存长期成绩，玩家可以投几个球，再继续走向教室或操场另一边。

## 二十二、六张旧球桌怎样变成乒乓球练习和比赛

篮球完成后，项目开始处理西侧六张固定砌筑式乒乓球桌。

乒乓球没有直接复用篮球系统。篮球是开放场景中的自由球体，乒乓球则需要固定机位、球拍输入、发球阶段、过网、落台、回合判定和对手 AI。Agent 因此为它建立了完全独立的控制器和局部物理，并让六张桌共用同一套比赛逻辑。玩家靠近任意一张球桌，都可以进入自由练习或先得7分的单人对战；离开后，原来的位置、朝向和校园行走状态会恢复，比分不会写入长期存档。

第一版虽然已经能打，却远远不是最终手感。用户在真实试玩中指出，比赛时第一人称视角仍会跟随鼠标旋转，球拍和镜头争抢同一组输入；机位离桌边太近，也看不完整张桌子。Agent 保留 Pointer Lock 提供的无限相对鼠标位移，但在比赛期间关闭自由转头，把相机后移并最终完全固定，让鼠标只负责球拍。

随后十多轮调整几乎都来自实际击球感受：球拍横向移动改为与屏幕同向；玩家球拍取消追赶延迟，直接跟随输入；拍面碰撞改为检查上一帧到当前帧之间的完整扫掠路径，避免快速挥拍时穿过小球；发球由自动击出改成先抛球，再等待下落时由球拍真正碰击；发球前球会跟随球拍定位，挥拍方向能够打出明显斜线；普通回球不再要求额外点击，而是只要拍面接触，并根据最近一小段真实挥拍方向决定横向角度、弧线和力度。

用户还连续调整了球速、抛球高度、鼠标灵敏度和虚拟拍面范围。这里的“虚拟拍面”不是把可见球拍偷偷放大，而是让碰撞容错略大于模型，使浏览器中的鼠标或触摸操作更接近人手持拍的感觉。乒乓球也采用与篮球相似的解析阴影：球在桌面上方时影子落在桌面，飞出桌外后自动转到校园地面，以帮助判断高度和落点。

这一过程特别清楚地说明，玩法不能只靠自动测试宣布完成。测试可以保证球会过网、会落台、会计分，输入不会失效，但“飘不飘”“跟不跟手”“能不能自然打出斜线”仍然需要人真正玩过之后判断。每次反馈都被翻译成一个较小的输入或物理变量，并尽量一次只改一个主要因素，再用回归测试保证前一轮已经成立的规则没有被破坏。

## 二十三、手机试玩怎样反过来推动性能与交互设计

乒乓球在手机上又暴露出桌面端看不到的问题。

最初触摸界面使用了多个 HTML 按钮和摇杆，但它们占据画面，也把“移动球拍”“挥拍”和“退出”拆成许多互相竞争的操作。后来这些按钮被移除，整块画布直接成为球拍控制区，进入比赛和退出改用场景中的三维按钮。普通回合只需移动手指，让球拍接触来球。

发球手势经历了两次相反的尝试。第一版是触摸按下立即抛球，结果同一次按下既要定位球拍，又已经让球离手，玩家还没站好位置就必须重新落指追球。用户在真机上试过后，要求改成“按住移动、松手抛球”：手指按下时球仍随拍移动，松开才从最后位置上抛；球在空中的时间也比桌面端略长，让玩家有时间重新落指控制球拍。实机反馈确认，这一版明显更顺手，因此成为手机端正式基线。

真机长时间试玩还帮助项目找到了一个更隐蔽的性能问题。用户发现，持续走动或连续打球一段时间后会逐渐卡顿；静止并停止产生声音一会儿，表现又会恢复。这条现象把调查范围从“手机整体性能不足”缩小到了音频生命周期。

检查后，Agent 为全场音效建立统一的活动声道管理。脚步、门窗、家具、粉笔、黑板、篮球、乒乓球和界面音效全部在播放结束后主动断开节点并移出活动集合；高频碰撞音按类别限制同时存在的声道数量，重复过密的声音会被丢弃。自动测试逐一播放各组音效，并模拟篮球弹跳、粉笔碰撞和乒乓球落台的密集突发，确认停止后活动声道能够回到零。

随后进行的渲染优化同样遵守单变量原则。项目关闭了浏览器每帧持续保留默认颜色缓冲的设置，降低手机显存带宽与合成压力，但没有同时降低像素比、关闭环境遮蔽、修改阴影、删减模型或引入 LOD。这样，用户在真机上的下一轮观察就能判断这一项修改本身是否有效，而不会面对一组无法区分来源的画质与玩法变化。

到这里，手机不再只是桌面版本的缩小适配。它成为项目的重要验证环境：触摸节奏由拇指和手指的实际动作决定，性能问题由持续试玩暴露，再由可测量的资源生命周期和单变量实验定位。

## 二十四、人的场景经验怎样推动了一次教室级 LOD 优化

2026年8月20日进行的教室渲染优化，是本项目中一次很典型的人机协作。它的起点不是 Agent 从通用性能清单中挑出一项技术，而是用户在持续试玩后提出了一个非常具体的场景判断：玩家站在一号楼时，没有必要让二号楼所有教室里的贴图、课桌和其他物品继续参与渲染；反过来也是一样。若玩家已经进入某间教室，其他教室甚至连简化课桌都没有继续绘制的必要。

这个判断包含了 Agent 无法只靠代码统计得到的知识。校园不是一个需要同时观看所有内部空间的展厅，而是一个以第一人称移动为主、由墙体和距离天然遮挡视线的环境。人的经验先指出了“玩家此刻真正可能看见什么”，Agent 再把它翻译成可执行的可见性规则、空间边界和切换条件。

第一步没有直接修改正式版本，而是先保留当时稳定代码并创建实验分支。Agent 先按教学楼划分室内渲染根节点：靠近或进入一号楼时，不让二号楼的完整教室细节参与绘制；靠近二号楼时同理。用户在实际运行中确认性能有明显改善，才决定沿这个方向继续，而不是仅凭理论上的 draw call 数量宣布方案有效。

第二步把粒度从整栋楼缩小到单间教室。每间教室的完整墙面材质、课桌、讲台、黑板、风扇、课本、宣传物和其他室内细节被归入独立渲染组。玩家进入教室，或接近教室门约3米时，该教室的完整内容才参与 draw call；离开时使用稍大的退出距离，形成滞回区，避免玩家在门槛附近轻微移动就让模型反复闪烁切换。

室外仍需要从门窗看到教室的大致结构，因此完全清空室内也不合适。Agent 为学生课桌制作了无贴图的简化替代体，随后根据用户观察继续补上讲台桌和黑板。这里再次出现了人和 Agent 各自擅长的部分：Agent 能生成低成本几何并用 InstancedMesh 合并绘制，用户却能立即看出第一版简化课桌像破碎模型，中间隔板缺失，整体轮廓不完整。Agent 据此重新调整几何，而不是用“它只是 LOD”解释视觉缺陷。

切换规则随后又增加一层。当玩家已经进入任意教室时，其他所有教室的简化课桌、讲台和黑板也全部退出绘制；只有玩家离开室内后，校园各教室的简化替代体才重新出现。这项规则利用了一个朴素但很有效的事实：人在封闭教室里不可能同时看到其他教室内部。它进一步减少了没有视觉贡献的 draw call，同时没有降低当前教室的质量。

优化过程中，用户还注意到二号楼室内在简化状态下露出黄色，走近后突然变白。这个问题不影响帧率，却会让优化切换被人眼直接察觉。Agent 因此为二号楼简化状态补上无贴图的白色室内墙壳，使远近状态保持同一综合色调。这个修正说明，LOD 不只是减少几何和材质，还必须管理两个状态之间的视觉连续性；如果切换本身造成闪动，性能收益也会以感官损失的形式被用户感知。

这一轮还带来一个意外回归。服务重启后，本地场景中的厕所、旧教室、教师宿舍、榕树和滑梯等 Meshopt 压缩 GLB 一度全部消失。最初看起来像是新可见性逻辑误伤了场景资产，但运行时检查显示它们的根节点根本没有创建。最终定位到本地 Vite 依赖缓存仍引用旧的 Meshopt 解码器哈希，开发服务器返回 `504 Outdated Optimize Dep`。Agent 强制重建依赖缓存恢复模型，并让这些关键资产在解码失败时阻止加载页放行，不再以“校园已经准备好”的假成功状态掩盖错误。

这次优化的价值不只是一组 LOD 代码。人的贡献是持续指出真正可见的空间、可接受的切换时机和肉眼不能接受的破损或色闪；Agent 的贡献是把这些判断实现为分层场景树、教室级激活、距离滞回、实例化简模、失败屏障和可回退的实验分支。性能提升来自两者的闭环：经验提出正确问题，技术把问题变成可测量、可验证、可以安全撤销的实现，再由真实试玩决定是否继续。

这也修正了项目早期对 LOD 的笼统判断。榕树多档 LOD 曾因轮廓损失而被否决，并不意味着所有 LOD 都不适合本项目。对于具有强空间遮挡、内部构件高度重复的教学楼，按教室管理细节是一种更符合玩家视线的 LOD。优化方案应针对对象和观看方式分别判断，而不应因为一次实验成功或失败，就把同一结论扩展到整个校园。

## 二十五、一台旧掌机怎样变成人与 Agent 共同拆解的记忆机器

Octopus 掌机的制作，是这个项目中另一种很典型的人机合作。它没有从建筑尺寸或空间关系开始，而是从一种很具体的怀旧体验开始：有些学生会把 Game & Watch 掌机带回学校，藏在课桌书仓里，课间拿出来玩。用户希望玩家在教室里发现这样一台掌机，点击后进入全屏，看到的不是现代仿制界面，而就是记忆中那台旧机器。

最初的技术方案虽然具备完整功能，却走错了视觉方向。Agent 用程序化几何表现机身，用 Canvas 和绘图函数画 LCD 人物、触手和数字。它可以响应按键，也可以计分，但用户很快指出，这种画面与原机相差太远。Game & Watch 的意义不仅在规则，更在泛黄塑料、红褐边框、灰绿色玻璃和彩色印刷底纹共同形成的物件感。如果主机和液晶图案都被重新画成近似图形，即使游戏“能玩”，也无法唤起玩家对旧掌机的记忆。

用户据此提出了决定性的改法：整台主机正面应该是一张写实图片，正式游戏时仍然直接显示这张图片；除了按钮反馈，主机大部分区域根本不需要运动。LCD 也不是一个可以自由绘画的现代屏幕。它由底层固定彩色印刷背景和上层许多预制液晶电极组成，所谓动画，只是这些固定图案按规则显示和隐藏。

这个判断推翻了原方案，也把问题变得更准确。Agent 随即把全屏表现改为二维正交图片合成：写实底图在下，活动液晶段在中间，玻璃观感在上；场景里的掌机只保留一个负责厚度和阴影的薄壳。运行时不再移动或重画人物，只需要回答一个问题：当前这一帧，哪些真实液晶段应该亮起？

真正困难的部分由此出现。全段点亮图里有潜水员、宝物、四条触手、数字、生命、模式文字和被抓姿态，它们有的彼此相邻，有的由多个断开的墨块共同组成。自动连通区域可以找到像素，却无法判断语义。一个断开的头、身体和四肢可能属于同一块电极；一片看似触手的形状，实际上可能是被抓潜水员挣扎时的一条腿。Agent 如果只靠图像距离自动归类，很容易得到一个数学上整齐、游戏上却无法使用的结果。

双方因此建立了一种新的中间语言：人工分色所有权图。Agent 先把液晶全亮图转换成保持原坐标的伪彩色基础图，用户直接在这张图上修改颜色。规则非常简单，却足够精确：一个可独立通断的物理电极使用一种颜色；同一电极即使包含多个不连通小岛仍然同色；需要分别闪动的两个形状必须异色。用户不需要写 JSON，也不需要先知道 Shader 或图集结构，只需要凭对原机图案和动画的理解判断“哪些形状应该一起亮”。

这项人工工作经历了多轮细化。用户有意删除了生成图里并不存在于原机的细小色块，发现两个极小区域其实是多余噪点，又指出某个编号段也不应保留。更关键的一次修正发生在触手划分上：Agent 原先把几块图形归入触手，用户看出它们属于被触手抓住的潜水员。随后用户进一步判断，被抓状态的身体应保持完整，而几只脚应当两条一组轮流闪动，形成挣扎。这个判断最终被编码为固定身体加两组腿交替的两帧动画。

过程中，用户还提出一个让流程明显简化的判断：既然人工颜色图已经完整表达了所有活动像素，就可以直接把它转换成统一的黑色液晶图，不必再维护另一张容易失配的黑色母版。Agent 据此把人工颜色图确立为物理轮廓的权威来源，并把这些视觉判断变成确定性生产流程。导入脚本检查每个放大色块是否为纯色，把人工颜色图规范化到真实 LCD 尺寸；每一种颜色生成一个物理段，同色的多个断开部分仍保留在同一段；全部段被打包进一张透明图集，并生成清单、编号图、逐段联系表和代表状态联系表。自动检查要求重叠像素、漏分像素、越界像素和全亮重建差异全部为零。用户不必手工裁出七十多张透明图片，Agent 也不能越过人的确认擅自解释图案。

这套分工不是“人帮机器做完它做不到的苦工”，而是把判断放回最合适的一方。人擅长从怀旧物件和动作含义中识别“这是谁的脚”“这是不是宝物”“这两块是否应该同时闪”；Agent 擅长保证几万个像素没有重叠或遗漏，把一次人工判断稳定地传播到图集、语义表、运行代码和测试。双方通过一张可直接编辑的颜色图完成协作，而不是要求人学习程序数据结构，也不是让 Agent 假装能够从像素中猜出全部原机逻辑。

资产进入运行时后，人机往返仍然继续。用户先后指出液晶太大、按键没有对准、游戏画面偏左，并要求液晶向右移动时不要带动原本位置正确的 `GAME A`、`GAME B` 状态栏。Agent 因此把活动游戏段和模式段分组，允许它们使用不同的偏移。用户又发现底图缺少左上小船、左侧绳子和右侧沉船尾杆，并特别提醒不要在已经反复修改的图片上继续精修。最终底图回到最早确认的高质量源图，在一次处理中补齐固定背景、清除活动液晶，只做无损裁边，不再经历多代生成。

玩法本身也通过实际观看不断纠正。第一版碰撞表让潜水员刚离开船就必然被第一条触手抓住，用户试玩后立即发现不合常理。Agent 检查状态表，确认出发位没有被作为安全位置单独保护，随后重新划分第一条触手的分支与碰撞范围。左下角 Game A、Game B 不亮的问题，则来自模式文字被当成静态底图或没有进入活动段清单；它们后来被从原位提取为两个独立液晶段，随模式互斥显示。

声音和界面也经历了相同过程。用户认为最初音效太单薄，要求研究原机声音而不是随意增加现代音乐。Agent 根据早期掌机的一位压电输出方式，把声音改成短方波脉冲和节拍组合，为移动、触手、取宝、返船、恢复、失误和结束分别建立音型，同时保持 TIME 演示静音。全屏顶部提示最初把电脑键盘和手机触控说明堆在一起，字体又大又亮；用户指出它干扰主机画面后，Agent 将桌面与触控提示分开，并改成小字号、低亮度的两行或三行布局。

退出按钮还暴露出一次更隐蔽的状态问题。为了阻止点击退出后同一次手势又触发校园画布，第一版代码会无条件吞掉“下一次点击”。如果浏览器没有产生预期的尾随 click，这个标记就会一直留下，把玩家随后点击竹竿的操作吃掉，于是竹竿看起来无论怎样点击都无法开始。用户不是通过代码日志，而是通过跨玩法的实际体验发现了它。Agent 最终把抑制条件缩小为750毫秒内、仍靠近退出按钮的同坐标点击，并增加“掌机退出后立即进入竹竿并成功蓄力”的串联回归。`Esc` 和右上角按钮也被统一到同一条恢复路径。

Octopus 最终形成的，不只是一台可以玩的掌机。它还产生了一套可迁移的方法：先确认写实主机，再制作无活动液晶的底图；用人工分色表达物理电极所有权；自动生成单色图集和零差异检查；由人确认语义与代表动画；运行时只切换固定段；最后在真实浏览器中校准对位、规则、声音、触控和模式生命周期。这套方法已经整理成独立制作指引，后续的 Manhole 和 Helmet 可以沿用同一框架，但仍要重新经历各自的人工判断。

这次合作补充了项目原有的那句话。校园空间中，人负责记得，Agent 负责把记忆变成可以验证的空间；到了旧掌机里，人还负责辨认那些像素真正意味着什么，Agent 则负责让这种意义成为可以精确显示、测试和反复运行的系统。

## 二十六、当前版本已经走到哪里

截至2026年8月22日，项目已经完成校园主要空间与五栋建筑的还原，建立了连续高台、围墙、校门、操场、沙池、运动设施、树木和滑梯；两栋教学楼具备可进入教室、走廊、台阶和楼梯；主要门窗和独立建筑已经替换为正式 GLB；墙面、地面、树木和设施形成统一的手绘水彩美术方向。

教室里已经有课桌、凳子、黑板、讲台、课本、作业本、宣传画、奖状、粉笔盒和粉笔。桌面与手机都可以从校门进入并在校园中行走。玩家能够开合门窗、坐下、在22块教学黑板上绘画、保存内容、拾取粉笔、蓄力抛掷、落地再拾取，并让粉笔回到粉笔盒。

校园现已接入统一的常用与交互音效。篮球具备拾取、投掷、推动、踢动、弹跳、滚动、投篮判断和动态落点阴影；西侧六张乒乓球桌均可进行自由练习与7分单人对战，并已根据桌面和手机的真实试玩完成多轮机位、发球、挥拍方向、速度和触控调整。

二号楼一间教室的课桌书仓中已经放入一台 Nintendo Game & Watch Octopus OC-22。玩家可以点击进入写实全屏掌机，使用键盘、鼠标或多点触控游玩 Game A、Game B 和 TIME。它使用人工确认的固定 LCD 段图集，具备取宝、返船、触手、碰撞、失误、Game Over、独立最高分和原机风格脉冲声音；退出后能够完整恢复校园状态，并与竹竿等其他玩法正常衔接。掌机制作过程也已沉淀为可供后续型号复用的专题指引。

运行时仍坚持基础校园完整预载，近距离使用完整模型；教学楼室内则采用按教室激活的细节层级，室外使用无贴图的简化课桌、讲台、黑板和二号楼白色室内墙壳，进入任意教室后停用其他教室的简化替代体。项目已经建立浏览器测试、性能预算、视觉基线、资产归档、本地用户数据层和统一音频生命周期管理，可以在不破坏当前成果的前提下继续增加故事、年代物件或新的互动。

仍然开放的部分主要属于继续精修，而不是从头补全：少数 C 级尺寸可以在新记忆出现后调整；手机端持续帧率、发热和横竖屏表现仍需继续用真机观察；更多个人故事、年代物件和小游戏可以继续扩展。

## 结语

这个项目最特别的地方，不是使用了 Three.js、Blender、图像生成或自动化测试中的某一种工具，而是这些工具被组织成了一套服务于记忆的过程。

人提供草图、参考、口述和感受，Agent 把它们整理成证据、图纸、参数、模型、材质和交互；人再走进场景，判断哪里像、哪里不像；Agent 根据新的判断继续修改，并把结果写回资料和测试。校园不是从一张图里被一次性“生成”出来的，而是在一轮轮观看和纠正中逐渐清晰。

如果用一句话概括这段开发经历，那就是：

**人负责记得，Agent 负责把记忆变成可以验证的空间；然后人走进这个空间，再帮助 Agent 把它变得更像记忆。**
