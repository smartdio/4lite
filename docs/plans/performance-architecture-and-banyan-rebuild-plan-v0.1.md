# 校园场景性能、结构优化与榕树重制实施计划 v0.1

更新时间：2026-08-16  
状态：阶段 0、阶段 1 已完成；下一步为独立阶段 2  
适用基线：第一阶段封板版本 `4fef288` 及当前工作区资源  
依据：`handoff.md` 第25节、2026-08-16 性能与代码结构审查

阶段 0 的实际迁移、体积变化与回归结果见 `docs/reports/phase-1-cleanup-report-v0.1.md`。归档完整清单位于 `archive/phase-1/manifest.json`，运行白名单位于 `archive/phase-1/runtime-whitelist.json`。

## 1. 目标

本计划用于把当前校园场景从“高性能电脑可运行的第一阶段基线”推进到以下目标：

1. 支持较广泛的 PC、手机和平板浏览。
2. 支持公网渐进加载，避免首次访问一次性下载全部高成本资源。
3. 在不改变已确认空间、尺寸、材质语言、交互和碰撞的前提下降低下载量、启动阻塞、内存、显存和逐帧渲染成本。
4. 将当前单体实现拆分为边界清晰、参数集中、可独立测试的模块。
5. 重新设计和制作大榕树，同时解决现有形体不满意与资源成本过高两个问题。

## 2. 不可回退项

- 不移动已确认建筑、设施、榕树中心或玩家活动边界。
- 不以优化为理由改变门窗交互、楼梯通行、地面高度或碰撞范围。
- `src/campus-config.js` 继续作为空间数据唯一来源，不建立第二套坐标。
- 保留 `window.__CAMPUS_TEST__` 的现有能力，并在拆分后通过兼容适配层维持调用方式。
- 不使用 `img2threejs` 或单图直接生成三维场景；榕树采用设定确认、人工／程序化建模、UV、贴图、LOD 和运行优化流程。
- 每项性能修改必须记录修改前后数据，并从固定相机与固定行走路线做视觉和行为回归。

## 4. 总体实施顺序

实施顺序调整为：

0. 清理发布边界与归档阶段文件。
1. 固化性能基线、预算和自动回归。
2. 独立完成新榕树的形体重设、正式资产、LOD、纹理与场景验收。
3. 在新榕树阶段封板后，另行建立通用资产规范并优化其余 GLB、贴图、加载和共享资源。
4. 建立桌面／移动端自适应渲染质量档。
5. 完成移动端交互和公网加载体验。
6. 小步拆分代码与集中参数。
7. 完成部署、缓存、兼容性和设备验收。

不得在一次提交中同时完成多个高风险阶段。每一阶段必须可独立回退。

所有迁移记录至少包含：

- 原路径
- 新路径

## 6. 阶段 1：性能基线、预算与回归

### 6.1 增加统一测量接口

在 `window.__CAMPUS_TEST__` 下补充：

- `renderer.info.render`：draw calls、三角面、线段和点。
- `renderer.info.memory`：纹理和几何数量。
- 当前绘制缓冲尺寸、DPR、GTAO 分辨率和阴影贴图尺寸。
- 各资产请求、下载、解析、GPU 上传和 ready 时间。
- 帧耗时的 P50／P95／P99。
- 当前质量档、降级原因和设备能力。
- 碰撞候选数，而不仅是碰撞体总数。

### 6.2 初始性能预算

| 指标 | 手机低档目标 | 桌面高档目标 |
| --- | ---: | ---: |
| 首次可观看下载 | 8–12 MB | 12–20 MB |
| 完整渐进加载 | 25–35 MB | 35–50 MB |
| 纹理显存估算 | 100–160 MB | 250–400 MB |
| 可见 draw calls | 120–150 | 200–250 |
| 可见三角面 | 40–70 万 | 100–150 万 |
| 稳态帧率 | 30 FPS 下限 | 60 FPS 目标 |
| 主线程启动长任务 | 单次 <100 ms | 单次 <100 ms |

预算可以根据代表设备测试调整，但调整必须记录原因，不能只提高阈值掩盖回退。

### 6.3 自动回归

- 把现有校门、楼梯、碰撞和门窗测试变为可由命令运行的浏览器测试。
- 保存固定相机列表和可比较截图。
- 每次资产改动记录构建大小、资源大小、draw calls、三角面和视觉差异。

### 6.4 执行状态（2026-08-16）

阶段 1 已完成。`window.__CAMPUS_TEST__` 已补齐 renderer、缓冲区、纹理估算、资产阶段、GPU 首帧批次、帧耗时分位数、设备能力与碰撞候选统计；六个固定相机、校门／楼梯／门窗回归和像素截图已接入 Playwright。统一命令为 `npm run test:performance`，CI 配置位于 `.github/workflows/performance-regression.yml`。实测与口径说明见 `docs/reports/performance-baseline-v0.1.md`；下一步严格进入阶段 2，不在本阶段顺手实施优化。

## 7. 阶段 2：新榕树独立重制阶段

本阶段只处理新榕树，从形体重新设计开始，到新资产接入和验收结束。它不是阶段 1 性能优化中的一个顺手项目，也不与阶段 3 的其他模型批量优化、阶段 4 的全局渲染质量档或阶段 6 的代码拆分合并实施。

大榕树不再以“继续压缩现有 v26”为唯一目标，而是重新建立形体和运行资产。现有 v26 只作为位置、尺度、碰撞和历史回退基线。

### 7.1 独立阶段边界

阶段输入：

- 用户对现有榕树形体不满意的反馈及现有榕树参考资料。
- v26 的位置、目标高度、地面贴合、碰撞和固定视角数据。
- 阶段 1 建立的性能测量方法和设备预算。

阶段交付物：

- 形体需求表和四向剪影／灰模评审材料。
- 用户确认后的高模或程序化源资产、LOD0／LOD1／LOD2、贴图和导出说明。
- 独立榕树资产清单、加载策略、失败回退和性能对比报告。
- 校园鸟瞰、地面近景、树下、宿舍方向的视觉验收，以及地面、阴影和碰撞回归。

阶段退出条件：形体评审和运行性能评审必须分别通过；任一未通过都不能覆盖 v26，也不能宣布阶段完成。阶段内不批量修改其他树木、门窗、沙池、建筑材质或全局渲染配置，避免把榕树的视觉决策和全场优化混为一次变更。

### 7.2 形体设计门槛

在进入正式三维制作前，先确认以下内容：

1. 正面、侧面、四分之三视角和校园鸟瞰中的总体剪影。
2. 树冠宽高比、重心、疏密和不对称方向。
3. 主干分叉高度、主枝走向、板根和气根密度。
4. 树冠是否分层、哪些区域需要透光、从地面看是否有清楚的枝干结构。
5. 土墩、石块底座与地面的关系。
6. 手绘动画感的色彩分组：亮叶、中间叶、暗叶、枝干、石块和土壤。

先提供低成本灰模或四向设定图，由用户确认剪影；未确认前不制作高成本贴图和细叶片。

### 7.3 新资产结构

建议拆为可独立 LOD 和共享材质的组件：

- 主干＋板根
- 主要枝干
- 气根组
- 近景叶簇
- 中远景叶冠块
- 土墩
- 石块底座

叶片优先使用少量高质量图集和实例化叶簇，不再用大量独立 Mesh。透明面应减少互相叠放，控制 overdraw；远景直接使用体块叶冠或低面叶簇，不保留近景卡片密度。

### 7.4 LOD 建议预算

| 级别 | 使用场景 | 三角面 | Mesh／draw calls | 纹理建议 |
| --- | --- | ---: | ---: | --- |
| LOD0 | 地面近看 | 35–60k | <=12 | 树皮 2K、叶片 1–2K、石土 1K KTX2 |
| LOD1 | 校园中景 | 12–25k | <=8 | 1K–2K KTX2 |
| LOD2 | 鸟瞰／远景 | 2–8k | <=4 | 512–1K KTX2 或叶冠体块 |

正式榕树目标：

- 最高 LOD 网络资源尽量控制在 5–8 MB 内。
- 最高 LOD 纹理显存估算控制在 32–48 MB 内。
- 鸟瞰默认优先加载 LOD2 或 LOD1；接近榕树时再加载 LOD0。
- 三个 LOD 的外轮廓、树高和根部落点保持一致，切换不得明显跳变。

### 7.5 位置与行为兼容

- 中心继续使用 `[22.72, -36.8]`。
- 目标高度继续以 `9.544 m` 为初始场景基准；形体确认后如需改变，只能由用户明确批准。
- 最低点仍按地面贴合，不额外手工抬高。
- 玩家碰撞初始保持半径 `1.00 m`，除非新树干实际包围盒要求小幅修正并通过现场验收。
- 新资产在测试期间使用新 URL，不覆盖 v26；验收通过后再切换资产清单。

### 7.6 榕树验收

形体：

- 校园鸟瞰、主操场、教师宿舍方向和树下近景均通过用户确认。
- 剪影不能只在单一视角成立。
- 树下能看到主干和主要枝条，不形成完全封闭的叶片球。

性能：

- 分别记录三个 LOD 的文件大小、纹理显存、Mesh、draw calls、三角面和透明覆盖成本。
- 手机低档默认不加载 LOD0。
- 榕树加载失败时保留低成本占位或 LOD2，不阻塞校园进入。

兼容：

- 原位置、地面贴合、石块底部、阴影和碰撞回归通过。
- 新旧资产固定视角对比可回退。

## 8. 阶段 3：其余资产与加载管线

本阶段不属于新榕树重制。只有阶段 2 的新榕树已经独立封板并保留可回退版本后，才开始把其中验证有效的压缩、LOD、纹理和加载经验推广到其他资产。

1. 建立单一 `GLTFLoader`、`KTX2Loader` 和 Meshopt 解码器实例。
2. 建立 URL → Promise 的资源注册表；相同 URL 只下载、解析和创建纹理一次。
3. 南侧与西南侧活动沙池共享同一模板，不再独立解析。
4. 门、窗和沙池共享公共玻璃、木材和水泥边框纹理。
5. PNG/JPEG/WebP 运行纹理逐步改为 KTX2；颜色／透明图和法线图分别选择合适模式。
6. 合并门窗 GLB 中同材质、同交互 Pivot 的碎片；保留交互能力但降低每个模板的 Mesh 数。
7. 树木和乒乓球台改为实例化；所有模型保持单一完整版本，不建立运行时 LOD。
8. 将资产分为入口关键、鸟瞰必要、近景延迟和空闲预取四级，不再一次性 `Promise.all` 全部资源。
9. 加入进度、失败重试、取消和低 LOD 回退。

## 9. 阶段 4：渲染质量档

建立 `performance-profiles.js`，集中管理：

- DPR／最大绘制像素数
- 抗锯齿
- GTAO 开关、分辨率、采样和模糊参数
- 阴影尺寸、距离、投影对象和刷新策略
- 描线开关和线宽
- 模型细节策略（现行固定为完整模型，不允许 LOD）
- 纹理等级和各向异性
- 最大并发加载数
- 目标 FPS 和自动降级阈值

初始建议：

- 低档候选：DPR 0.75–1、GTAO 关闭、1024 阴影、叶片不投影；模型仍使用正式完整版本。
- 中档候选：DPR 1、半分辨率低采样 GTAO、1536 阴影；模型仍使用正式完整版本。
- 高档：DPR 1–1.25、当前风格 GTAO、2048 阴影；模型使用正式完整版本。

阴影从启动时即关闭自动更新；资产按批次加入后节流刷新一次。门窗动画在低档不逐帧刷新整座校园阴影。

鸟瞰静止时采用按需渲染；页面隐藏时暂停动画和状态 DOM 更新。

## 10. 阶段 5：手机、平板与公网体验

- 左侧虚拟摇杆移动，右侧拖动观察，单独交互按钮。
- 处理触摸拖动、门窗点击和双指缩放之间的冲突。
- 适配横屏、竖屏、安全区和浏览器动态工具栏。
- 首屏先显示校园低成本轮廓和加载进度，允许用户尽早旋转查看。
- 低带宽／省流模式仍使用正式完整模型，但延后非入口关键资产并停止后台预取；不建立低 LOD。
- WebGL2、纹理压缩或内存不足时给出明确降级信息。
- 部署使用内容哈希 URL、CDN、长期 immutable 缓存和正确 MIME；支持非域名根路径部署。

## 11. 阶段 6：代码模块化与参数集中

目标结构：

```text
src/
  app/bootstrap.js
```
