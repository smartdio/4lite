# 写实 LCD 掌机制作与接入指引

更新时间：2026-08-22
状态：依据 Octopus OC-22 已完成流程整理，供 Fire、Manhole、Helmet 及后续同类掌机复用

## 1. 目标与基本原则

本指引适用于 20 世纪 80 年代固定段式 LCD 掌机。目标不是把旧游戏改画成现代小游戏，而是在写实原机正面中，只让真实液晶电极按原机规则显示和隐藏。

必须遵守以下原则：

- 全屏外观以确认过的写实正视图片为主体，不用程序化几何、Canvas 绘图或矢量人物重画主机正面。
- 固定彩色印刷背景与活动液晶分层。海水、道路、建筑等印刷图案不参与动画；活动人物、障碍、数字和状态文字才是液晶段。
- 每个活动图案保持原始像素、位置和形状。运行时只显示或隐藏，不平移、不变形、不逐帧重画。
- ImageGen 用于建立统一写实资产，不负责决定游戏语义。段的归属和动画组合必须经过人工确认。
- 每一个阶段单独验收。前一阶段未确认，不批量扩展，也不接入正式运行时。
- 精修始终回到最早确认的高质量源图一次完成。不要连续修改多代派生图片，否则文字、边缘和材质会持续劣化。
- 不依赖 ROM；规则、节拍、声音和状态表独立实现，并清楚标记实测值、资料值与候选值。

## 2. 交付物总览

每台掌机最终应具备以下资产和数据：

1. 原始参考图与来源说明。
2. 确认的写实主机正视源图。
3. 正式主机底图：包含外壳、印刷文字、固定彩色 LCD 底纹和玻璃观感，不包含活动液晶。
4. 场景静态 TIME 合成图，或可由底图与 TIME 段确定性合成的配置。
5. 人工分色所有权图。
6. 单色透明液晶段图集。
7. 物理段清单与源文件哈希。
8. 语义段清单与代表状态联系表。
9. 正常按钮坐标、扩大触摸命中区和按下反馈。
10. 独立玩法状态机、节拍表、声音表和存档命名空间。
11. 资产检查图、运行截图、专项测试与构建结果。

推荐目录结构：

```text
docs/references/handheld/<game>/        原始照片、说明书与资料说明
docs/previews/<game>-handheld-v01/      生成稿、人工分色图与全部验收图
public/assets/handheld/<game>/           正式运行资产
src/interactions/data/                  段清单和语义布局
src/interactions/                       独立玩法控制器
tests/performance/                      玩法、输入、生命周期与移动端回归
```

## 3. 阶段门与确认顺序

必须按以下顺序推进：

### Gate A：型号与参考资料

- 确认型号、系列和正面按钮布局，避免混入同名重制版或相邻型号。
- 用户照片与记忆优先；其他照片只补足缺失的材质、侧面和尺寸信息。
- 版本差异必须提前确定。例如相同正面可能存在电路或规则修订，不能在实现中无意混用。
- 尺寸来源不可靠时标记为工作值，不写成实测。

### Gate B：写实正视稿

- 正交正视、完整四边、无透视、无手、无环境、无水印。
- 保留原机比例、塑料、金属、磨损与轻微老化，不重度做旧。
- 主参考图决定布局；其他同系列照片只能补充年代感，不能带入不同按钮或文字。
- 每轮只修一个明确问题，直到用户确认主机整体外观。

### Gate C：正式底图

- 从最早确认稿一次清除全部活动液晶。
- 同一次精修补齐遗漏的固定印刷背景、绳索、船体、边杆和模式框等细节。
- 不从多轮修改后的低质量派生图继续修补。
- 输出后核对像素尺寸和自然比例；只允许无损裁边，不为适配工作尺寸拉伸图片。
- 活动的 `GAME A`、`GAME B`、MISS 等状态不能烘成常亮底图。

### Gate D：人工分色所有权图

- 用户确认全部物理电极的边界和归属。
- 自动生成全亮图、编号图和逐段联系表。
- 重叠、漏分、越界、重建差异均为 0 后冻结物理段。

### Gate E：语义与代表动画

- 给每个物理段分配游戏语义。
- 确认人物移动、障碍变化、被抓／被击中、数字、模式和 TIME 演示的代表状态。
- 语义覆盖完整、无重复后冻结布局版本。

### Gate F：运行时对位

- 在桌面、横屏和竖屏中核对底图、液晶和按钮。
- 必要时允许整组段统一缩放或偏移，但固定模式栏等特殊组必须支持独立偏移。
- 用户确认实际运行画面后，才能更新视觉基线。

### Gate G：玩法与节拍

- 规则、碰撞、得分、失误、Game A/B、TIME、声音和存档全部通过。
- 使用可信说明书和原机录像逐帧校准；没有资料时明确标记候选节拍。

## 4. 人工分色规范

人工分色图是最关键的源文件，也是物理 LCD 轮廓的权威来源。确认采用人工分色后，不再要求额外黑色母版。

### 4.1 文件格式

- 使用 PNG，不使用 JPEG。
- 背景为纯白 `RGB(255,255,255)`。
- 每个物理液晶电极使用唯一、不透明的 RGB 颜色。
- 不使用透明度、渐变、羽化、抗锯齿、阴影、半透明画笔或颜色管理效果。
- 建议以真实 LCD 像素尺寸的 4 倍编辑，放大和缩小都使用 Nearest Neighbor。
- 每一个 4×4 块必须为完全相同的纯色；导入脚本发现混色块时应直接失败。

### 4.2 颜色与电极的关系

- 一个颜色代表一个可独立通断的物理电极。
- 同一电极即使包含头、身体、四肢等多个不连通小岛，也必须使用同一种颜色。
- 两个需要分别闪动或分别碰撞的电极，无论多接近，都必须使用不同颜色。
- 不同电极绝不能因为看起来属于同一人物、触手或工具而共用颜色。
- 不要追求颜色好看；颜色只用于表达所有权。优先选择彼此差异明显的颜色，避免肉眼误认。
- 极小色块也要判断语义，不能仅因面积小自动删除。确认是生成噪点或多余像素后才移除，并记录原因。

### 4.3 常见误分

- 把“被抓人物”的脚或工具误归到触手／障碍。
- 把两组轮流闪动的腿合成一个段，导致无法形成挣扎动画。
- 把宝物与携带宝物的人物合成一个段，导致不能独立显示。
- 把数字保存成十张完整数字图，而不是每一位的真实七根电极。
- 把固定彩色背景误当作液晶前景。
- 相邻形状因为颜色相同被自动合成一个段。

### 4.4 用户介入方式

系统先提供一张保持原坐标的伪彩色基础图，用户直接在该文件上修改颜色。用户无需填写 JSON，也无需精确书写段名，只需遵守“一个电极一种颜色”。

每轮修改应：

1. 从最新指定的人工分色源继续编辑，不修改自动生成的编号图或单色图。
2. 保持画布尺寸不变。
3. 只用硬边填色和最近邻缩放。
4. 明确说明有意删除的形状，防止脚本误判为丢失像素。
5. 保存为新版本，不覆盖已经确认的上一版。

## 5. 自动导入、切分与验证

Octopus 的现行参考脚本为：

- `scripts/image/import_octopus_manual_recolor.py`
- `scripts/image/build_octopus_manual_segment_package.py`
- `scripts/image/build_octopus_semantic_layout.py`

这些脚本目前包含 Octopus 的硬编码路径和少量已确认清理点。制作新掌机时应复制并泛化配置，不能直接改写 Octopus 的已冻结输入。

### 5.1 规范化

导入脚本应执行：

1. 检查宽高可被编辑倍率整除。
2. 检查每个放大块为纯色。
3. 用最近邻规则还原 1× 所有权图。
4. 统计前景颜色数、前景像素数和相对上一版的新增、删除、换属像素。
5. 对用户明确确认的噪点进行有记录的确定性清理。
6. 输出规范化 1×、规范化 4×和 JSON 指标。

禁止模糊缩放、颜色聚类和自动“修好”边缘。这些操作会改变用户确认的电极轮廓。

### 5.2 生成物理段

- 所有非白色像素都是液晶前景。
- 每种颜色生成一个物理段；同色的多个连通区域保留在同一段中。
- 段编号按固定空间顺序生成，保证同一输入得到同一结果。
- 每段输出：`atlasRect`、`screenRect`、像素数、连通区域数、检查颜色和候选分组。
- 所有段打包到一张带透明通道的共享图集。
- 清单记录所有权图 SHA-256；源图变化后必须重建整套图集和清单。

必须满足：

```text
overlapPixels = 0
unassignedPixels = 0
outsidePixels = 0
reconstructionDifferentPixels = 0
```

### 5.3 四种验收图

每次物理段变化都重新生成：

1. 全段单色点亮图：验证全部段组合能重建人工分色轮廓。
2. 伪彩色编号图：检查边界、漏块和颜色误合并。
3. 逐段联系表：每格只显示一个段及像素／连通块信息。
4. 代表状态联系表：显示游戏开始、中途、碰撞、失误、Game Over、模式和 TIME 等组合。

人工确认的重点不是“段数是否符合预期”，而是每一个可独立变化的图案是否拥有独立控制权。段数只能作为异常提示，不能反过来决定图案归属。

## 6. 物理段与语义段分离

物理清单只回答“哪些像素一起通断”；语义清单回答“这个段在游戏中是什么”。二者必须分文件保存。

推荐语义命名：

```text
player.position.0
player.hit.static.0
player.hit.legs.pose.0
obstacle.1.extension.2
item.position.3
life.0
digit.2.a
mode.gameA
clock.pm
```

语义映射要求：

- 每个物理段必须且只能映射到一个语义 ID。
- 语义 ID 不重复。
- 标记 `candidate` 或 `confirmed`，未经人工确认的触手顺序、工具轨迹和碰撞组合不能伪装成事实。
- 数字按显示位与电极命名，例如 `digit.2.a`，再由字形表组合 0–9。
- 障碍伸长使用累积段列表；被抓、跌落等特殊动画使用明确的帧集合。
- 物理图集变化后重新验证语义覆盖，不通过则禁止构建正式资产。

## 7. 运行时显示结构

推荐继续使用当前 Octopus 的结构：

- 一张写实底图。
- 一张共享透明液晶图集。
- 一个合并后的 `BufferGeometry`。
- 每个段一个固定四边形，UV 指向 `atlasRect`，位置来自 `screenRect`。
- 每个段四个顶点携带 `enabled` 属性。
- Shader 最终透明度为 `atlasAlpha × enabled × opacity`。
- 状态变化只更新 `enabled` 缓冲，不更新 CanvasTexture，不替换材质，不创建新网格。

逻辑层只输出段集合：

```js
resolveVisibleSegments(gameState) => Set<segmentId>
```

同一状态必须始终产生同一集合。随机性只决定下一次状态，不直接操纵渲染对象。

对位调整遵循以下顺序：

1. 先校正底图裁切与自然比例。
2. 再校正 LCD 屏幕矩形。
3. 再做液晶整体缩放。
4. 最后做液晶整体偏移。
5. 模式栏等原本正确的特殊组使用独立偏移，不跟随游戏画面误移。

## 8. 主机、按钮与场景陈设

- 全屏模式是独立正交场景和纯黑背景，不受校园灯光、透视、后处理或色调映射影响。
- 场景陈设复用同一写实正面，只增加负责厚度、阴影的薄壳。
- 正常按钮保留在底图。按下时在同一图片坐标覆盖压暗或按下态；不需要全屏 3D 按钮。
- 按钮布局使用主机图片归一化坐标，不能依赖屏幕像素或场景薄壳坐标。
- 每个按钮配置精确可见反馈区域和更大的不可见触摸命中区。
- 多点触控按 `pointerId` 独立持有；移出、`pointercancel`、`lostpointercapture`、窗口失焦和退出都必须释放。
- 场景交互使用独立轻量代理、距离限制和遮挡判断，不递归扫描完整教室。

## 9. 玩法状态机与原版校准

### 9.1 先列状态，再写代码

针对每台掌机先整理：

- 玩家固定位置及可用移动方向。
- 障碍或敌人的固定位置、增长顺序和分支。
- 每个碰撞位置对应哪些段组合。
- 得分、奖励、失误、恢复、Game Over 与循环规则。
- Game A/B 的规则差异和节拍表。
- TIME 的时钟格式和自动演示段组合。
- 特殊动画由哪些静态段与交替段构成。

不要从当前画面“看起来差不多”推断碰撞。Octopus 曾出现出发位一离船就必定被抓的问题，原因正是碰撞表没有把安全出发位单独保护。

### 9.2 资料优先级

1. 原机说明书。
2. 可逐帧检查的原机录像。
3. 可信模拟器或官方重制版，用于交叉验证而不是直接复制代码。
4. 玩家记忆和照片。
5. 无法确认的内容保留为候选值。

录像校准应记录基础 tick、不同分数阶段、Game A/B 差异、碰撞停顿、得分停顿和 Game Over 时长。测试模式允许固定时钟和随机种子。

### 9.3 声音

- 先确认原机声音硬件能力，再设计声音；不要为了“丰富”擅自添加原机不存在的持续音乐。
- 固定段式早期掌机通常适合用短方波脉冲、节拍和蜂鸣组合。
- 移动、障碍、取物、得分、奖励、失误和结束分别定义音型。
- TIME 演示是否静音以原机为准。
- 复用现有 AudioContext 生命周期和并发限制，窗口失焦与退出时停止残留音序列。

## 10. 模式生命周期与输入清理

进入掌机时：

- 检查当前必须处于可进入的校园模式，并与其他小游戏互斥。
- 保存玩家位置、相机四元数、FOV、Pointer Lock、流送细节锁定状态。
- 清空行走按键、速度、拖动和触摸状态。
- 暂停校园输入和环境模拟，隐藏普通 HUD。
- 显示掌机正交场景，并默认进入 TIME。

暂停与退出掌机时：

- 桌面端按 `X` 直接调用 `exit()`；按 `Esc` 打开统一 WebGL 暂停菜单，“继续游戏”关闭菜单并恢复原局，“返回校园”调用掌机的 `exit()`。右上角按钮仍直接退出，触控端不增加暂停步骤。
- 结束当前局、保存最高分、恢复 TIME，释放全部键盘和指针所有权。
- 恢复玩家、相机、FOV、教室细节、环境声音、行走控制和原 Pointer Lock 意图。
- 退出按钮在 `pointerup` 且指针仍位于命中区时才生效。
- 为防同一手势的尾随 `click` 再次触发校园，只能短时、同坐标抑制；禁止无条件吞掉“下一次点击”，否则会破坏竹竿、黑板等后续交互。

每台掌机必须增加串联回归：

```text
掌机 -> Esc暂停 -> 继续 -> 原局与计时正常恢复
掌机 -> Esc暂停 -> 返回校园 -> 进入另一小游戏 -> 能立即操作
掌机 -> 按钮退出 -> 进入另一小游戏 -> 能立即操作
另一小游戏 -> 退出 -> 进入掌机 -> 能立即操作
```

## 11. HUD 与响应式布局

- HUD 继续使用 WebGL／Three.js，不增加校园内 HTML 浮层。
- 提示采用小字号、低亮度灰暖色和半透明暗底，不与液晶争夺视觉焦点。
- 桌面端只显示键盘操作；触控端只显示触控操作，禁止把两套说明堆在一起。
- 桌面可使用两行“玩法＋键盘”；手机可使用三行“玩法＋操作＋模式”。
- 退出按钮视觉尺寸保持克制，但不可见命中区至少 44×44 CSS 像素，并完整位于安全区域。
- 设备类型或视口变化时立即重算帮助版本、按钮坐标和正交相机，不只在首次进入时计算。
- 竖屏保持整机可见，不裁掉实体按钮；触摸命中区可扩大，但不得与邻近按钮重叠。

## 12. 存档、配置与模块边界

每台掌机使用独立、版本化命名空间：

```json
{
  "version": 1,
  "highScores": { "gameA": 0, "gameB": 0 }
}
```

- Game A/B 最高分独立保存。
- 当前局不跨退出恢复。
- 损坏、缺字段或旧版本数据安全回退。
- 校园配置只记录资产 URL、摆放、尺寸、LCD 对位、按钮坐标、交互距离和规则参数。
- 每种游戏保留独立控制器；可抽取共享的写实 LCD 渲染器、按钮所有权和模式生命周期辅助层，但不要把不同游戏规则塞入一个巨大控制器。
- 测试构建公开模式、段集合、按键、资产状态和存档快照；正式构建不暴露测试 API。

## 13. 测试清单

### 资产

- 仅存在指定数量的掌机实例。
- 场景摆放、朝向、尺寸和遮挡正确。
- 图集哈希与清单匹配。
- 段重叠、漏分、越界和重建差异均为 0。
- 逐段显示不夹带相邻图案。

### 视觉

- 底图没有活动液晶残留。
- 固定印刷背景完整，没有因多轮修图损失细节。
- LCD 缩放、偏移、墨色和玻璃观感正确。
- 模式栏、数字和游戏图案按各自分组正确对位。
- 桌面、横屏和竖屏按钮均对准。
- 按下反馈不改变按钮形状或错误遮挡文字。

### 玩法

- 每个逻辑状态输出精确段集合。
- Game A/B、TIME、得分、碰撞、失误、奖励和 Game Over 完整。
- 安全出生位、边界位置和同时事件经过专项验证。
- 正式随机与固定种子测试结果都合理。

### 输入与生命周期

- 键盘、鼠标、触摸、多指、移出、取消、失焦无卡键。
- `Esc` 暂停菜单的“返回校园”与退出按钮恢复同一状态；“继续游戏”恢复原局且不吞掉后续输入。
- 退出后可立即使用座位、黑板、竹竿及其他小游戏。
- Pointer Lock 恢复符合进入前状态。

### 性能与发布

- LCD 热路径只更新 `enabled` 缓冲。
- 无逐帧纹理上传、材质创建和完整场景射线扫描。
- 核对新增请求、纹理体积、显存和绘制调用。
- 执行定向 Playwright 回归。
- 执行 `npm run build:test`、`npm run build` 和 `npm run perf:build`。
- 未经用户确认不更新视觉基线。

## 14. Octopus 经验总结

以下问题已经实际发生，后续掌机必须主动避免：

- 程序化绘制的机身和 LCD 与原机质感差距过大，即使玩法正确也无法产生怀旧感。
- 让 ImageGen 分别生成每个动作会造成位置、颜色和边缘不一致；应生成统一图案后人工确定所有权。
- 自动连通区域不能决定语义；一个人物可能由多个不连通墨块组成，相邻触手也可能粘连。
- 人工分色图本身可以直接成为权威轮廓，不需要再维护一张容易失配的黑色母版。
- 仅按预期段数判断会误删真实的小电极，或保留生成噪点；必须看编号图和逐段联系表。
- 被抓潜水员不是一整张闪烁图：固定身体常亮，两组腿交替，才能形成挣扎。
- 活动模式文字不能留在静态底图；应当作为独立段显示。
- 全局 LCD 偏移可能修正人物却破坏模式栏，因此运行时必须支持按组对位。
- 从多次修补后的图片继续 ImageGen 精修会显著降低文字和细节质量；最终底图要回到最初确认源图一次完成。
- 退出后无条件吞掉下一次点击会让其他小游戏看似失效；尾随点击抑制必须绑定时间和坐标。
- 同时展示桌面和触控说明会形成视觉噪音；帮助内容必须按设备分流。
